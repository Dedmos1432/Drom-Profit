## Фактические типы и ограничения

`S = 9007199254740991` — `Number.MAX_SAFE_INTEGER`, `M = 9223372036854775807` — положительный предел PostgreSQL BIGINT. `L = 1000000000000` — исследуемый предел в рублях. В действующем OpenAPI все поля ниже имеют тип `integer` без `format: int64` и без максимума. В таблице указаны декларируемые минимумы. Общие алиасы OpenAPI используются в ответах, запросах создания и PATCH. В PATCH пропуск поля оставляет его значение прежним. Значение `null` разрешено только для полей, где оно указано.

## Как воспроизведено

Проект Compose `drom-mvp-money-audit`, Linux Docker, PostgreSQL 17.6 `drom_profit_test` на tmpfs, отдельная мигрированная схема, без публикации портов. Core проверен через FastAPI TestClient с фактическими запросами и PostgreSQL. В запросах передавались исходные JSON-литералы, включая `2.0`, `1e3` и числа за пределами BIGINT. Точные суммы фиксировались из исходного тела ответа до декодирования JavaScript. После записей перечитывались карточки и флаги, цена также сверялась отдельным SELECT. Для импорта подставлен локальный Parser callable через существующий адаптер. Demo оставался единственным штатным источником.

Web-проверка использовала оригинальные MSW-обработчики и изолированный storage. Оригинальные клиентские валидаторы, виджет цены и экран Comparison получили сохранённый сырой JSON Core. Невалидная разница проверена в UI, ввод — на штатных схемах форм. Внешних запросов не было. Временные диагностические файлы не входят в Git.

В Web `S+1` и `S+2` после чтения JSON становятся одним числом `9007199254740992`. На типизированном чтении карточки ошибка API-клиента не возникает, виджет `Price` показывает «Не указано». Форма цены и рыночной оценки также пропускает последнюю дробь после округления `Number`. Форма фактора требует строку цифр и отклоняет все три записи. На HTTP-входе Core отклоняет все три.

Во всех строках Core сохранил цену и указанные факторы и вернул HTTP 200 на Summary. Точные числа из тела Core приведены в порядке R / B / C / E. Mock принимал отдельные безопасные значения, а ошибку суммы выдавал при расчёте.

При `E₁=S` и `E₂=−1` каждый Summary отдельно безопасен, а `difference_from_min=S+1`. Core вернул 200 с точной разницей 9007199254740992. Mock ответил `422 amount_out_of_range`. В Web экран сравнения показал сообщение о некорректном результате, таблица скрыта. При граничной паре предложения `E₁=2L` и `E₂=1−L` Core и Mock вернули 200 и точную разницу 2 999 999 999 999. PATCH цены на S+2 вернул Core 200, сохранил точное значение и сбросил оба флага. Mock вернул 422, оставил прежнюю цену и оба подтверждения. При последующих PATCH цены на M+1 и `null` обе реализации вернули 422 и сохранили состояние каждой карточки. PATCH существующего расхода на S+2 прошёл только в Core, сбросив только подтверждение расходов. PATCH на M+1 отклонён обеими реализациями с сохранением состояния. PATCH на `null` и на 0 прошли в обеих, сохранили различие значений и сбросили только подтверждение расходов.

Python `int` S+2 сохранился точно, а входной `float` уже округлился до S+1. Текущий `json.loads` JSON-LD может передать такой `float` при десятичной или экспоненциальной записи. Нормализация приняла целочисленный `1000.0`, но отклонила дробный `1.5`, строку `"1e3"`, ноль и bool. Эти наблюдения относятся к нормализации и адаптеру на локальных данных. Пути потери точности независимы. Отдельный столбец ограничен BIGINT, агрегаты Python могут выйти за него. Любой из R, B, C, E и разницы может оказаться небезопасным для JavaScript. Безопасный E не подтверждает безопасность составляющих. Двоичный `Number` в Web и `float` в JSON-LD могут потерять цифры до проверки. Поэтому нужен инвариант на входе и при сохранении группы, а также проверка ответа на границе клиента. ## Рекомендуемый контракт

Предложение для согласования — целые рубли JSON `integer`, общий лимит `L = 1 000 000 000 000` для входных денежных значений и двух агрегатов карточки. `L` — технологический потолок MVP. Он оставляет запас для любых допустимых сумм и сравнений, не меняя JSON-тип и назначение полей. Фактическая уместность потолка для продукта и источника требует подтверждения.

| Поле и смысл | Минимум | Максимум | Неизвестное |
|---|---:|---:|---|
| Цена сохраняемой карточки и `listing_price` в расчёте | 1 | 1 000 000 000 000 | Запрещено |
| Цена предпросмотра `ListingData.price` | 1 | 1 000 000 000 000 | `null` при отсутствии цены |
| `market_valuation` | 1 | 1 000 000 000 000 | `null` для отсутствующей оценки |
| `Expense.amount`, `Benefit.amount` | 0 | 1 000 000 000 000 | `null`, сохраняется отдельно от известного нуля |
| `total_expenses` = R | 0 | 1 000 000 000 000 | Число по известным расходам |
| `total_benefits` = B | 0 | 1 000 000 000 000 | Число по известным преимуществам |
| `acquisition_cost` = C | 1 | 2 000 000 000 000 | Запрещено |
| `adjusted_cost` = E | −999 999 999 999 | 2 000 000 000 000 | Запрещено |
| `difference_from_min` | 0 | 2 999 999 999 999 | `null` для всех карточек при `double_count` |

При `1 ≤ P ≤ L` и `0 ≤ R,B ≤ L` имеем `1 ≤ C = P+R ≤ 2L` и `1−L ≤ E = C−B ≤ 2L`. Разница для любого набора без конфликта лежит в `0…(2L−(1−L)) = 0…(3L−1)`. Нижний E достижим при `P=1, R=0, B=L`. Верхний E достижим при `P=L, R=L, B=0`. При совместном выборе этих карточек разница равна `3L−1`. Все операции с неотрицательными частичными суммами и знаковыми производными лежат внутри безопасного диапазона `Number`, `Long` и BIGINT. Число записей в группе на доказательство не влияет. Для равных E сохраняются несколько нулевых разниц. При неизвестных суммах обновляются счётчики и статус полноты по действующим правилам. Отрицательный E сохраняется с действующим предупреждением Comparison. Рыночная оценка остаётся отдельной величиной.

## Предложение по OpenAPI и ошибкам

Во всех перечисленных свойствах оставить JSON `type: integer`, добавить `format: int64` для генераторов Kotlin и явно задать `minimum`/`maximum` из таблицы. Сохранить `nullable`, `required` и разделение запросов создания и PATCH. Обновить `CarInput`, `CarPatch`, `Car`, `ListingData`, схемы факторов, `Summary` и `ComparisonItem`, включая переиспользуемые поля. Текущая генерация TypeScript отображает `integer` в `number`. Для денежных полей описать допустимую JSON-запись прямо в контракте. Предложение — целочисленный JSON-литерал в десятичной записи. Ведущий минус учитывается при проверке диапазона. Запись `-0` имеет значение 0, клиенты сериализуют его как `0`. Дробь, точка с нулевой дробной частью, экспонента, число в кавычках и логическое значение получают `422 validation_error`. Целое с недопустимым знаком рассматривается как выход за диапазон. Mock должен проверять исходный денежный литерал до стандартного `JSON.parse`, если нужна та же строгая грамматика прямых API-вызовов. После `JSON.parse` равные `2.0` и `2` уже неразличимы. Формы отправляют канонические числовые поля и сохраняют явный `null`. Текстовый ввод проверяется как последовательность цифр до преобразования в `Number`. Для источника импорта правила пробелов, текстовой валюты и точной десятичной записи задаются отдельно.

- **POST и PATCH денежных полей.** `422 amount_out_of_range` для корректного целочисленного литерала вне диапазона или результата записи, который вывел бы R/B за предел. Пример ответа `{"code":"amount_out_of_range","message":"Сумма выходит за допустимый диапазон рублей."}`. Для агрегата сообщение называет группу. При нескольких нарушениях сначала возвращать `validation_error` за ошибку структуры. Схема `Error` и HTTP 422 уже есть, в описаниях соответствующих ответов нужно закрепить код, условия и примеры. Формат ошибки сохраняется для старых клиентов.
- **Импорт.** Известная неподдерживаемая цена или рыночная оценка источника даёт действующий `502 parse_error` по предложению. Предпросмотр с отсутствующей ценой возвращает `200` и `price: null`. Для сохранения покупатель явно вводит цену. Решение, должен ли заведомо некорректный необязательный показатель блокировать весь предпросмотр, требует согласования.
- **Summary и Comparison.** При соблюдении инварианта все итоги гарантированно допустимы. Рекомендуемый выпуск зависит от проверки и согласованного исправления существующих нарушений. Если потребуется переходный режим для уже сохранённых карточек, отдельно согласовать `422 amount_out_of_range` для Summary/Comparison таких карточек и доступ к их исправлению. Внезапное нарушение после выпуска рассматривается как внутренняя ошибка целостности и диагностируется сервером. Ответ 200 с округлённым или обрезанным денежным результатом не предусмотрен.
- **Клиенты.** Web и Android показывают понятное сообщение, сохраняют введённые правки и текущую сессию. `422` не сбрасывает Bearer и не инициирует автоматический повтор записи. Существующие ошибки `validation_error`, `parse_error` и ошибки доступа сохраняют свои роли.

## Существующие данные и миграция

Проверка выполняется под учётной записью только чтения, на разрешённом снимке или реплике, с согласованным временем выполнения. Она выводит только количества. Суммы расходов и преимуществ считаются отдельно, чтобы JOIN не размножал строки. PostgreSQL возвращает `numeric` для `sum(bigint)`, приведение цены и рыночной оценки оставляет сложение и модуль точными и для старых значений. Ширина диапазона E считается по сессиям, без выдачи ID. Она показывает потенциально небезопасное Comparison внутри сессии. Конфликт `double_count` может подавить разницы для конкретного набора.

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY;
SET LOCAL statement_timeout = '30s';

WITH expense_totals AS (
    SELECT car_id, sum(amount) AS total, max(amount) AS largest
    FROM expenses GROUP BY car_id
), benefit_totals AS (
    SELECT car_id, sum(amount) AS total, max(amount) AS largest
    FROM benefits GROUP BY car_id
), amounts AS (
    SELECT c.session_id, c.price AS p, c.market_valuation AS m,
           coalesce(x.total, 0::numeric) AS r, coalesce(b.total, 0::numeric) AS b,
           x.largest AS largest_expense, b.largest AS largest_benefit
    FROM cars c
    LEFT JOIN expense_totals x ON x.car_id = c.id
    LEFT JOIN benefit_totals b ON b.car_id = c.id
), values_by_car AS (
    SELECT *, p::numeric + r AS c, p::numeric + r - b AS e FROM amounts
), spreads AS (
    SELECT max(e) - min(e) AS max_difference
    FROM values_by_car GROUP BY session_id HAVING count(*) >= 2
), limits AS (
    SELECT 1000000000000::numeric AS cap, 9007199254740991::numeric AS js
)
SELECT count(*) AS cars,
       count(*) FILTER (WHERE p NOT BETWEEN 1 AND cap) AS price_outside_cap,
       count(*) FILTER (WHERE m IS NOT NULL AND m NOT BETWEEN 1 AND cap) AS valuation_outside_cap,
       count(*) FILTER (WHERE largest_expense > cap) AS expense_outside_cap,
       count(*) FILTER (WHERE largest_benefit > cap) AS benefit_outside_cap,
       count(*) FILTER (WHERE r > cap) AS total_expenses_outside_cap,
       count(*) FILTER (WHERE b > cap) AS total_benefits_outside_cap,
       count(*) FILTER (
           WHERE p > js OR abs(m::numeric) > js OR r > js OR b > js OR c > js OR abs(e) > js
       ) AS cars_with_unsafe_js_money,
       (SELECT count(*) FROM spreads CROSS JOIN limits WHERE max_difference > js) AS sessions_with_unsafe_js_spread
FROM values_by_car CROSS JOIN limits;

ROLLBACK;
```

Запрос проверен на временной мигрированной БД. На 43 искусственно заполненных карточках он нашёл 10 цен, 8 оценок, 7 групп расходов и 8 групп преимуществ за пределами предлагаемого L. Небезопасные для JavaScript поля или итоги были у 15 карточек, потенциально небезопасная разница — в 3 сессиях. Эти числа описывают тестовые данные. Пользовательская БД не обследовалась.

Порядок внедрения после утверждения:

1. Запустить аудит с чтением на актуальном снимке. Если обнаружены нарушения, согласовать с владельцами корректировку исходных данных и способ информирования. Сохранить исходные значения для проверки. Нулевая рыночная оценка рассматривается отдельно от неизвестной. Автоматических замен, обрезания и удаления не предусматривается.
2. На копии проверить исправления старых данных и будущую версию API. Релиз блокируется до устранения нарушений либо согласования явного переходного режима. Именованные ограничения строк можно добавить с `NOT VALID`, затем выполнить `VALIDATE CONSTRAINT` отдельным шагом после проверки. `NOT VALID` пропускает первоначальное сканирование, но сразу проверяет новые и изменяемые строки.
