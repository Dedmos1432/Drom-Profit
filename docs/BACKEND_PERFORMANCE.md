# Нагрузочная устойчивость Core Backend

Этап 8.6.1, INT-09. Исходная точка — чистое рабочее дерево `integration/mvp` на `abe2899184f0b8e1145b34ec6d833ca0dc3584d1`, синхронизированное с `origin/integration/mvp`. Проверки выполнены в `C:\DromProfit\Drom-Profit-integration`.

## Воспроизведение

Запускайте команды из `backend/`. Подготовьте отдельный локальный env-файл с новым паролем PostgreSQL по инструкции Backend. Именем проекта ниже может пользоваться только эта проверка. В командах укажите путь к подготовленному файлу. Для сравнения версий снимайте результаты на одной машине одним и тем же диагностическим сценарием. [Создание локального env-файла](../backend/README.md#создание-локального-env)

```powershell
$perfEnv = 'C:\path\to\performance.env'
docker compose -p drom-mvp-performance --env-file $perfEnv --profile test build tests
docker compose -p drom-mvp-performance --env-file $perfEnv --profile test up -d --wait postgres-test
docker compose -p drom-mvp-performance --env-file $perfEnv --profile test run --rm --no-deps tests
docker compose -p drom-mvp-performance --env-file $perfEnv --profile test run --rm --no-deps tests python -m pytest -q -s -p no:cacheprovider tests/load_postgres.py
docker compose -p drom-mvp-performance --env-file $perfEnv --profile test run --rm --no-deps -e DROM_LOAD_CLIENTS=50,100 -e DROM_LOAD_WAVES=2 tests python -m pytest -q -s -p no:cacheprovider tests/load_postgres.py
docker compose -p drom-mvp-performance --env-file $perfEnv --profile test down
```

Каждый конкурентный клиент по умолчанию выполняет пять сценариев. Каждый сценарий создаёт отдельную сессию и две карточки, добавляет расход и преимущество, подтверждает группы для обеих карточек, запрашивает Summary и Comparison. Тест проверяет суммы и разницу с минимумом. После ошибки тест начинает следующий сценарий. Поэтому исходные уровни с ошибками обработали меньше запросов, чем полные прогоны. Основной замер и повторные волны запускаются последовательно. В повторных волнах для каждого числа клиентов сохраняются тот же Uvicorn, пул и схема БД. [Нагрузочный сценарий](../backend/tests/load_postgres.py)

Для сопоставления с `abe2899` исходный код можно развернуть через `git archive abe2899` в отдельный временный каталог. Для диагностического baseline перенесите туда только `backend/tests/load_postgres.py` и `backend/tests/performance_probe.py` из этого этапа. Соберите исходный образ с теми же версиями зависимостей и повторите команды в изолированном проекте. Короткий эксперимент с лимитером использовал параметры `-e DROM_LOAD_CLIENTS=100 -e DROM_LOAD_ROUNDS=2 -e DROM_LOAD_THREAD_TOKENS=80` в `docker compose run`. Основной прогон и повторы используют штатное значение AnyIO.

Процентили HTTP включают локальный транспорт, работу клиентов и сервера и ошибки. Скорость — обработанные HTTP-запросы в секунду. Диагностика выдаёт метрики отдельно по маршрутам, время блокирующего вызова очереди пула, checkout → checkin, число токенов AnyIO и SQL-время, включая локальный обмен с БД. `pg_stat_activity` наблюдается с отдельного соединения раз в 200 мс, планирование event loop — с шагом 50 мс. Короткие ожидания могут пройти между пробами. CPU — нагрузка Python-процесса относительно одного ядра, RSS — его максимум с начала процесса. Python-процесс включает Uvicorn и генератор нагрузки. Ресурсы PostgreSQL в эти цифры не входят.

Инструментализация включается только при явном запуске нагрузочного теста. Она выводит агрегаты, классы исключений, SQLSTATE и шаблоны маршрутов. Тела запросов, токены и SQL-параметры в отчёт не попадают. Замеры до и после использовали одинаковый сценарий с этой диагностикой. [Инструментализация](../backend/tests/performance_probe.py)

## Baseline и первопричина

Отдельный исходный сценарий из `abe2899` без новой диагностики завершил 431/500 сценариев на 100 клиентах, вернул 69 ответов `500`, P95 составил 6012 мс. На 1, 10 и 50 клиентах исходный сценарий прошёл. Расширенный сценарий был запущен на том же исходном серверном коде до исправлений и повторно зафиксировал дефект.

В коротком диагностическом прогоне 100 клиентов × 2 сценария завершились 146/200, поймано 54 SQLAlchemy PoolTimeout. В зафиксированном окне все 40 токенов AnyIO заняли вызовы, ожидавшие соединение из QueuePool. Ещё 60 задач ожидали поток. Все 15 соединений удерживали Summary, уже ожидавшие проверки ответа. PostgreSQL показывал до 15 `idle in transaction`, до одного активного подключения и отсутствие зарегистрированных ожиданий `Lock`. P95 SQL составил 45 мс, P95 очереди пула — 4918 мс. После волны все выданные соединения вернулись в пул.

FastAPI 0.165.0 выполняет синхронные обработчики через общий лимитер AnyIO. В `serialize_response` валидация ответа синхронного обработчика также получает токен этого лимитера. FastAPI закрывает синхронную yield-зависимость с `scope="function"` после валидации и до отправки HTTP-ответа. Финализатор использует отдельный limiter. Очередь задерживала этап, после которого финализатор только мог начаться. Снимок на baseline оставался открыт до этого этапа. Таймауты освобождали токены, после чего часть запросов продолжала работу. При 80 токенах в том же коротком эксперименте и пуле 10+5 завершилось 200/200 сценариев, без HTTP-ошибок, с 69,67 запроса/с и P95 2459 мс. Это подтверждает роль планирования потоков. В основном прогоне оставлены штатные 40 токенов.

| Гипотеза | Наблюдение |
|---|---|
| Сессии чтения держат соединения после расчёта | Подтверждено измерением удержания на этапе валидации ответа и регрессионными тестами. |
| No-op PATCH удерживает блокировку и соединение | Подтверждено для расхода, преимущества и заметки. Этот маршрут не входит в основной нагрузочный цикл. |
| Утечка соединений | После каждой завершённой волны baseline выданных соединений и ожиданий в пуле 0. Оставшиеся `idle` не имеют открытой транзакции. |
| Конфликты строк и лимит PostgreSQL | У клиентов отдельные карточки. В проблемном окне зарегистрировано 15 `idle in transaction` при лимите PostgreSQL 100 и без зарегистрированных `Lock` или ошибок SQLSTATE. Отдельные тесты проверяют блокировки на одной карточке. |

## Жизненный цикл и изменения

Создание `Session` не забирает соединение. Первый SQL либо `flush` начинает транзакцию и получает checkout. `commit` завершает транзакцию записи. Контекст `session_for` закрывает сессию и откатывает незавершённую транзакцию, включая выход по исключению. Закрытие возвращает соединение. В обычном ходе авторизация и бизнес-операция используют подключения последовательно. [Реализация сессий](../backend/app/db.py)

| Операции | Граница транзакции после исправления |
|---|---|
| Авторизация защищённых маршрутов | `require_session` читает ID по хешу Bearer и закрывает свою сессию до вызова обработчика. |
| `POST /api/session` | Чек-аут при записи, commit до формирования HTTP-ответа. |
| `POST /api/cars/import` | Авторизация заканчивается перед ожиданием Demo Parser. Предпросмотр не пишет в БД. |
| Список, карточка, Summary и Comparison | Результат целиком формируется в `REPEATABLE READ READ ONLY` внутри синхронного обработчика. Закрытие и rollback возвращают соединение до валидации HTTP-ответа. |
| Создание, PATCH карточки и удаление | Создание выполняет INSERT и commit. PATCH, подтверждение и удаление блокируют карточку по владельцу, используют `READ COMMITTED` и `FOR UPDATE` с ограничением ожидания блокировки 3 с. Commit перед ответом. |
| Создание, PATCH и удаление расходов, преимуществ и заметок | Блокировка той же карточки. Изменение денежного фактора и сброс флага фиксируются вместе. PATCH с совпадающими значениями завершает транзакцию и освобождает блокировку до валидации ответа. |

Синхронный read-обработчик завершает работу контекста в том же потоке, который получил соединение. Прерывание ожидания ответа клиентом само по себе не прерывает SQL и не отменяет состоявшийся commit. При выходе синхронной операции по исключению сессия откатывает незавершённую работу. Для async-импорта во время ожидания источника соединение отсутствует. В этом этапе не моделировалось принудительное завершение процесса или обрыв сети во время commit. ## Конфигурация и ответы при перегрузке

Размер пула, таймауты и число workers оставлены прежними. Каждый worker владеет своим пулом. Суммарный максимум Backend равен `workers × (pool_size + max_overflow)`. Например, два процесса со штатным пулом дают 30 потенциальных соединений. При настройке production оставьте запас для миграций, обслуживания и прочих потребителей той же БД. Замеряйте P95/P99, утилизацию CPU, checkout и SQLSTATE по процессам. Оцените задержки и I/O на конфигурации целевого окружения, включая разный размер карточек и длительный трафик.

В действующем контракте `503 source_unavailable` относится к источнику импорта. Исчерпание пула, временная недоступность PostgreSQL, lock timeout и транзакционный конфликт имеют разные причины. Текущий Core отдаёт для них `500 internal_error` с отдельными сообщениями там, где это предусмотрено. Для управляемого отказа при перегрузке предлагается согласовать отдельный `503 database_overloaded` и условия `Retry-After`. Отсутствие соединения до начала транзакции и потеря связи во время commit требуют разной обработки. При неизвестном исходе записи повтор денежных POST требует предварительного решения по идемпотентности. [Обработчики БД](../backend/app/db.py) · [Контракт](../shared/openapi.yaml)

Тот же драйвер выполнял девять операций на сценарий. Инструментализация очереди и потоков в этом эксперименте была выключена.

Эксперимент одновременно меняет распределение нагрузки и локальные пулы, поэтому не даёт отдельной количественной оценки каждого фактора. Основное исправление убирает зависимость возврата соединения от валидации, а итоговые волны используют один worker и исходный пул.

## Функциональные проверки

## Статус и границы проверки

INT-09 закрыт для локального сценария из девяти API-операций. Три прогона на 100 клиентах выполнили по 500/500 сценариев при том же пуле и без использования источника Дрома. Итог применим к этому сценарию и локальной конфигурации. PostgreSQL в тестах использовал tmpfs, клиенты совершали последовательные операции по локальной сети, у каждой сессии были отдельные небольшие карточки. Длительная производственная нагрузка, 150 клиентов и деградация внешних зависимостей не проверялись. Перед выпуском отдельно согласуйте критерии задержек и контракт перегрузки, затем замерьте нагрузку на целевой инфраструктуре. [INT-09](INTEGRATION_BACKLOG.md)
